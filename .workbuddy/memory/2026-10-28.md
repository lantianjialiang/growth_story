# 2026-10-28 · 成长档案网站 MVP 落地

## 做了什么
按 `growth-archive-spec.md` 实现完整 MVP（M0–M5），项目根即仓库，npm workspaces 三包：
- `packages/shared`：zod schema、DTO、日历日期 + 精度工具（年龄计算）
- `apps/server`：Hono + better-sqlite3 + Drizzle，路由/服务/媒体流水线/导出/回收站
- `apps/web`：Vite + React 19 + Tailwind v4 + TanStack Query + i18n(zh/en)

## 关键技术决策
- **不用 pnpm**（环境无），改用 npm workspaces + `concurrently`。
- 迁移手写 `apps/server/drizzle/0001_init.sql` + 自建 `__migrations` 执行器，避开 drizzle-kit 生成的不确定性（`db:generate` 仍保留配置）。
- 会话 Cookie + argon2id（@node-rs/argon2）；CSRF 用 SameSite=Lax + Origin 校验。
- 媒体：`sharp` 重新编码（丢弃全部 EXIF/GPS）+ 480/1600 WebP；`exifr` 以 `reviveValues:false` 读原始 EXIF 字符串，避免时区漂移；sha256 去重。
- 年龄算法：按月推进取最大整月，解决 1/31→3/1 负数；2/29 生日平年按 3/1。
- 权限唯一入口 `requireProfileAccess(level: view|edit|manage)`，无权限统一 404。
- Hono `route('/api/v1', ...)` 下，子路由 `/` 会挂到 `/api/v1`（不是 `/api/v1/`），档案路由必须写成 `/profiles`。

# 2026-10-28（续）· 服务端被图片请求打崩（线上级 bug）

## 现象
`npm run dev` 启动几秒后进程退出：`TypeError [ERR_INVALID_STATE]: Invalid state: ReadableStream is already closed`，
栈在 `ReadableByteStreamController.close` ← `internal/deps/undici` ← 微任务。

## 根因
`c.body(fs.createReadStream(...) as unknown as ReadableStream)`（媒体、导出、`app.ts` 静态资源三处）。
`@hono/node-server` 对 Node 流走 `Readable.toWeb()` 适配，并且 `writeFromReadableStreamDefaultReader`
里挂了 `writable.on('close', () => reader.cancel())` —— 响应正常结束后 cancel 会 destroy 底层文件流，
文件流的 `close` 事件再让适配器 close 一次已经关闭的 controller。异常在微任务里抛，路由 try/catch 抓不到，进程直接挂。

## 修复
- 新增 `apps/server/src/lib/fileStream.ts`：`streamFileBody(path)` 自己封装 Web ReadableStream，
  close/error/cancel 全部幂等（`settled` 标志 + try/catch），带 pause/resume 背压，cancel 时 destroy 文件流。
  三处调用点（media、export、静态资源）全部换掉。
- `index.ts`：加 `uncaughtException`/`unhandledRejection` 兜底（记 error 后继续跑），
  但 `server.on('error')` 单独处理监听失败（EADDRINUSE）→ `process.exit(1)`，避免「进程活着但不服务」。
- `packages/shared/tsconfig.json` 开 `incremental` + `tsBuildInfoFile: dist/.tsbuildinfo`：
  否则 `dev:shared` 的 tsc --watch 每次启动都重写 dist，触发 tsx 重启，dev 启动瞬间 vite 代理报 ECONNREFUSED。

## 验证
- 复现脚本（40 次请求到一半 `req.destroy()`）：修复前 **2 次就打死进程**，修复后 80 次顺序 + 40 次并发取消，health 恒为 200。
- 完整下载字节与磁盘一致（thumb 1498B / medium 10704B / 前端 JS 477794B 全等），Content-Length 正确。
- 无头 Chrome 打开分享页（含图）后服务存活，页面正常。
- 新增 `fileStream.test.ts` 4 例（完整读、提前 cancel、二次 cancel 幂等、文件缺失报错），合计 49 例全通过。
- Windows 上 `npm run dev` 被 kill 后子进程会残留占端口：用 `Get-CimInstance Win32_Process | ? CommandLine -like '*growth_story*'` 清理。

# 2026-10-28（续）· 第二轮反馈：归档语义 + 画廊翻页

## 1. 「归档」被理解成下载导出
用户点了管理页的「归档档案」（原语义是 `archivedAt` 从列表隐藏），以为是打包下载。
- **删掉 `archivedAt` 的 UI 开关**（档案列表本来就没有入口查看已归档档案，属于死路功能；DB 字段与 `?archived=true` 接口保留，需要时可恢复）。
- **归档 = 归档下载**：管理页新增 `ArchiveCard`（原 `ExportTab` 重写），放在基本信息卡片与「删除档案」之间。原来独立的「导出」标签页删除，TABS 变为 信息/成员/分享链接/回收站。
- 卡片内容：说明（带档案名）+ 三条要点（记录转 JSON / 原图按年月分目录 / 清单可被别的工具读）+ 主按钮（生成归档 → 正在打包 → 下载 ZIP）+「重新生成」。
- i18n：`manage.export.*`、`manage.tab.export`、`manage.archive/unarchive` 全部换成 `manage.archive.*`（title/hint/item1-3/start/processing/started/download/again/failed）。

## 2. 画廊里换照片不要换上下文
原来的 `go(delta)` 直接 `setIndex(index+delta)`：一条记录有多张照片时，按 → 会跳到下一条记录，标题/展签/胶片条一起变，胶片条还会平滑滚动 → 「来回跳」。
- `go()` 改成**照片优先**：先在当前记录内翻照片，最后一张之后才换记录；往回翻时落在上一条记录的最后一张（连续手感）。
- `canPrev`/`canNext` 替代原来的 `index` 判断，箭头不再在「最后一条但照片没翻完」时消失；aria-label 区分「上一张照片/上一件」。
- 只换照片时**只让主图淡入**：`img` 加 `key={photo.id}` + `.photo-in`（240ms opacity，`prefers-reduced-motion` 关掉），展台 `exhibit-enter` 仍只跟着 `current.id` 走。
- 胶片条与多图缩略条**只在当前项不可见时才滚动**（原来无条件居中，导致来回滚）。
- 预取逻辑改为先取同记录下一张，再取下一件主图；`photos` 用 `useMemo` 包住避免每帧重建数组。

## 5. 下拉框裁切 / 成员下拉 / 图片提速 / 可读落盘目录（第六轮）
- **下拉框文字被裁（用户反馈「角色里的文字没显示全」）**：原生 `<select>` 用 `.input`（`py-2.5`）再叠 `h-9` 时，内容盒只剩 14px，文字被上下切掉。新增 `.select` / `.select-sm`（`index.css`）：`appearance-none` + 上下内边距归零 + 固定高度（42px / 32px）+ 自绘 SVG 箭头 + `:disabled` 变淡；全站 11 个 select 全部从 `input` 改成 `select`（UsersPage、ManagePage 分享/成员/角色、SettingsPage 语言、DateField 年月日），UsersPage 三个输入框去掉 `h-9` 与下拉框对齐。README 加了「下拉框不要用 .input」的提醒。
- **成员邀请改成下拉**：新增 `GET /api/v1/profiles/:id/member-candidates`（manage 权限；排除所有者、自己、已在成员里的、已停用的账号，按昵称排序）；`MembersTab` 用 `useMemberCandidates` 渲染 `<select>`（选项显示「昵称 · 邮箱」），没有候选时提示去「账号管理」并给 admin 一个链接。
- **图片提速**：`processImage` 改成 `sharp(buffer).rotate()` 一条 pipeline + `clone()` 派生三份并行编码（源图只解码一次）；三份写盘并行；**浏览器送上来的图若已摆正且无 EXIF/XMP/IPTC/ICC 就直接留用原字节**，不再二次编码；去重改为先算 sha256 再决定要不要处理；上传路由用 `lib/concurrency.ts` 的 `runPool` 3 路并行（`os.availableParallelism` 取上限）；`rotateBuffer` 按格式高质量重编码（原来 `toBuffer()` 默认 q80 会掉画质）；前端 `MediaUploader` 改成边压边传（2 路压缩，压好一张就入队上传）。基准：单张 4032×3024 从 ~930ms → ~280ms；HTTP 实测 3 张 12MP 共 0.75s。
- **落盘目录可读**：新 key 为 `<档案名>-<档案id8>/<YYYY-MM 拍摄月>/<原文件名-slug>-<媒体id8>/original|thumb|medium`；`pipeline.ts` 新增 `slugifyName`（保留中文、去 Windows 非法字符、避开 CON/NUL 等保留名）、`buildMediaKeyPrefix`、`dirnameOfKey`；`processImage` 接受 `keyPrefix`（原地重写）或 `keyInput`（按 EXIF 拍摄时间归档）；`media` 表加 `original_name`（迁移 `0004_media_original_name.sql`）。迁移脚本 `scripts/rehome-media.ts`（`npm run media:rehome`，支持 `--dry`，按 `original_name → altText → 事件标题` 取文件名，幂等）已把 24 张老照片搬进 `小满-77bde782/2020-06…2026-10` 这样的目录。
- **顺手修的真 bug**：回收站里「彻底删除照片」以前只删数据库行、磁盘文件留在原地（留下孤儿目录）。现在 `trash.ts` 单条彻底删除会先删文件再删行（handler 改成 async），`StorageDriver` 新增 `pruneEmptyDirs()`，删完把变空的目录一并清掉；`purgeExpiredTrash` 与「彻底删除档案」也接上了。
